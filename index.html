Digital Forensics

PCAP → conversation → contentA supplied packet capture.

Wireshark (windows-2) · tshark (windows-36) · zeek (windows-18)

  1. Open the capture in Wireshark. Choose Statistics → Conversations; select a relevant peer pair and apply its conversation filter.
  2. Select a packet, then Analyze → Follow → TCP Stream (or the matching supported protocol). Inspect both directions.
  3. For transferred files, use File → Export Objects → the matching protocol; save only the relevant object to a new file.

Expected: A readable exchange or exported object tied to a specific conversation.

If stuck: For a large capture, use Zeek summaries to choose a stream; use TShark only when repeated field extraction is needed.

Caveat: Encrypted payloads need supplied keys; missing packets may prevent reconstruction. Keep original captures.

Verification: Source-reviewed; not executed on competition machines.

Disk image → partition → fileA raw disk image named disk.img; replace filenames and uppercase placeholders below.

The Sleuth Kit (windows-23) · Autopsy (windows-34) · TestDisk and PhotoRec (kali-143)

  1. mmls disk.img: record the filesystem partition Start sector as OFFSET; for a filesystem-only image use OFFSET 0.
  2. fls -r -o OFFSET disk.img: locate the desired path and record its metadata address as INODE.
  3. icat -o OFFSET disk.img INODE > recovered.bin: write to a new output name, then inspect the recovered bytes.

Expected: A path and metadata address, followed by the selected file contents.

If stuck: If listing fails, check image type and offset first; use Autopsy for GUI inspection or PhotoRec only when filesystem metadata is unusable.

Caveat: Sleuth Kit is recorded in WSL. Offsets are sectors; use the actual sector size if not 512 bytes. Deleted recovery may be incomplete; fls does not recurse into deleted directories.

Verification: Source-reviewed; not executed on competition machines.

Memory image → process leadA Windows memory image memory.raw and compatible locally cached symbols.

volatility3 (windows-31) · Volatility 2 (kali-151)

  1. From the installed Volatility 3 directory, run python3 vol.py -f memory.raw windows.info to check image and symbol recognition.
  2. Run python3 vol.py -f memory.raw windows.pstree to find unusual process/parent relationships.
  3. Run python3 vol.py -f memory.raw windows.cmdline; correlate arguments with the PID and parent you selected.

Expected: A PID, parent and command line that identify the next artifact to inspect.

If stuck: On symbol errors, resolve the matching symbols before trusting output. Use Volatility 2 only for a supported legacy image with its matching profile.

Caveat: Volatility 3 runs in WSL and uses symbols, not Volatility 2 profiles. Prepare symbols before offline use; a missing process row does not prove absence.

Verification: Source-reviewed; not executed on competition machines.

  • volatility3 — official documentation
Image, audio or PDF → inspect the matching formatA local file; choose just the branch matching its format.

ExifTool (windows-14) · pngcheck (kali-108) · zsteg (windows-12) · Audacity (kali-10) · qpdf (windows-26)

  1. PNG/BMP: run exiftool -a -u -g1 image.png; for PNG run pngcheck -v image.png. If pixel data is the clue, run zsteg image.png and validate meaningful hits.
  2. Audio: open in Audacity, open the track menu and select Spectrogram. Adjust Spectrogram Settings frequency range and window size; inspect channels separately.
  3. PDF: run qpdf --list-attachments document.pdf and qpdf --show-pages document.pdf; use a listed object number with qpdf --show-object=OBJECT document.pdf.

Expected: Metadata/chunk findings, visible time-frequency patterns, or PDF attachment/object identifiers.

If stuck: No meaningful result: revisit the format clue. zsteg is for PNG/BMP, not every image; a blank spectrogram may need different display settings.

Caveat: Keep originals. ExifTool, zsteg and qpdf are WSL entries. pngcheck version is unknown; metadata and stego signatures need corroboration.

Verification: Source-reviewed; not executed on competition machines.

Malware Analysis

Unknown executable → format and capabilitiesA sample copied into a local analysis directory.

Detect It Easy (DIE) (kali-27) · capa (kali-19) · FLOSS (FLARE Obfuscated String Solver) (kali-43)

  1. Open the file in Detect It Easy and record format, architecture and probable packer.
  2. For a supported executable named sample.bin, run capa -v sample.bin; record capability names and supporting addresses.
  3. Open a relevant match location in the native-code route; inspect the surrounding function before accepting the capability claim.

Expected: A format hypothesis and code locations worth investigating.

If stuck: If packed or unsupported, select a matching extraction route; use FLOSS only when hidden strings are the specific blocker.

Caveat: Signature and capability matches are leads, not observed execution. Static inspection does not require running the sample.

Verification: Source-reviewed; not executed on competition machines.

oletools (full suite: olevba, oleid, oleobj, rtfobj, mraptor, msodde, olemeta, oletimes, pyxswf) (kali-98) · Didier Stevens Suite (pdfid.py, pdf-parser.py, oledump.py and others) (kali-30)

If stuck: No VBA is not a clean verdict: inspect embedded objects with the matching oletools utility; an encrypted or malformed file may block parsing.

Identified bundle → extracted filesA file already identified as PyInstaller, Electron ASAR or UPX.

pyinstxtractor-ng (kali-111) · asar (@electron/asar) (kali-9) · UPX (kali-149)

  1. PyInstaller: run pyinstxtractor-ng sample.exe; record the reported Python version and inspect the extracted directory.
  2. Electron: run asar list app.asar, then asar extract app.asar extracted-asar into a new directory; inspect package.json and its entry point.

Expected: Extracted source/bytecode or an unpacked executable for static inspection.

If stuck: If the matching extractor fails, verify the format; modified packers and unsupported bytecode need manual reversing.

Caveat: Choose one matching branch. Extraction does not execute or decompile the payload; Python version determines decompiler support. UPX approval is 4.2.4.

Web Security

HTTP request → one controlled changeA working request to the assigned challenge service.

Burp Suite Community Edition (windows-20) · Google Chrome (windows-5) · curl (kali-23)

  1. In Burp Proxy → HTTP history, select the request and choose Send to Repeater.
  2. Send it unchanged; record status, response body and relevant cookies.
  3. Change one parameter or header, send again, then restore the baseline. Compare content as well as status.

Expected: A repeatable response difference attributable to one input.

If stuck: If the baseline fails, refresh authentication/CSRF values and confirm the host before testing a hypothesis.

Caveat: Burp Community is recorded in WSL; these steps need no Professional scanner. Keep requests and session tokens local.

Verification: Source-reviewed; not executed on competition machines.

  • Burp Suite Community Edition reference
Missing endpoint → bounded discoveryAn assigned base URL and a short local path list paths.txt; replace https://challenge.example.

ffuf (kali-41) · SecLists (kali-126)

  1. Request a unique nonexistent path in the browser; record its status, size and body to recognize wildcard responses.
  2. Run ffuf -w paths.txt -u https://challenge.example/FUZZ -rate 10 -t 1 -maxtime 60 -ac against the assigned host.
  3. Open promising hits manually and compare them with the nonexistent-path response.

Expected: Candidate paths whose responses differ from the calibrated baseline.

If stuck: Uniform responses may be wildcard pages or authentication redirects; recalibrate before increasing the list.

Caveat: The rate/time bounds are starting limits, not event permission. Approved ffuf is a development build; confirm flags locally and locate SecLists data rather than assuming a path.

Verification: Source-reviewed; not executed on competition machines.

Observed vulnerability → targeted testA reproducible request plus evidence for a specific vulnerability class.

PayloadsAllTheThings (offline copy) (kali-103) · sqlmap (kali-132) · Burp Suite Community Edition (windows-20)

  1. Open the matching topic in the local PayloadsAllTheThings copy; check its prerequisites against the observed input and response.
  2. In Repeater, change only that input using a relevant example; compare with the original request and a negative control.
  3. Only for suspected SQL injection: save the valid raw request as request.txt, replace PARAM, then run sqlmap -r request.txt -p PARAM --batch --level=1 --risk=1 --threads=1.

Expected: A reproducible class-specific response or sqlmap detection evidence for the selected parameter.

If stuck: A negative or inconsistent result means revisit the hypothesis, encoding and session state; do not escalate to broad scanning by default.

Caveat: References may name unapproved software. This SQL step detects; it does not request database dumping. Restrict testing to the assigned service.

Verification: Source-reviewed; not executed on competition machines.

  • PayloadsAllTheThings (offline copy) reference
  • sqlmap reference
JWT → claims → server behaviorA token from a working request to the assigned application; replace TOKEN locally.

jwt_tool (kali-77) · Burp Suite Community Edition (windows-20)

  1. From the installed jwt_tool directory, run python3 jwt_tool.py TOKEN to inspect header and claims.
  2. Run python3 jwt_tool.py TOKEN -T to change one relevant claim using the local prompts; retain the original token.
  3. Use Repeater to compare the original request, the modified token and a missing-token control; check actual protected content.

Expected: A server-side acceptance or rejection tied to the changed token.

If stuck: If every request fails, renew the baseline token and check expiry, audience and cookie placement before interpreting the test.

Caveat: Decoding is not signature validation. A modified unsigned/invalid token should be rejected; acceptance must be confirmed from server behavior. Installed jwt_tool version is unknown.

Verification: Source-reviewed; not executed on competition machines.

Reverse Engineering

Native checker → validation logicA native executable and its expected input format.

Ghidra (windows-22) · gdb (windows-9) · x64dbg (windows-33)

  1. In Ghidra, create a local project, import the executable, open it in CodeBrowser and accept analysis.
  2. Use Search → for Strings to find a prompt or success/failure text; follow its references to the checking function.
  3. Read the decompiler alongside the disassembly; rename input variables and record the comparison or transformation.

Expected: A concrete input check with its data flow and success condition.

If stuck: If static reasoning leaves a runtime question, use GDB in the matching native environment or x64dbg for Windows PE.

Caveat: Ghidra and GDB are WSL entries. Decompilation can mislead; x32dbg is needed for 32-bit Windows targets. Run unknown code only in the intended isolated analysis environment.

Verification: Source-reviewed; not executed on competition machines.

  • Ghidra beginner student guide
APK/DEX → validation methodA supplied APK or DEX, inspected without installation.

jadx (jadx-gui) (kali-72) · Apktool (kali-8)

  1. Open the file in jadx-gui; inspect the manifest/package tree to locate the application entry points.
  2. Search for a visible prompt or success/failure string; use Find Usage to reach the validation method.
  3. Trace the input through comparisons and transforms; note any method JADX cannot reconstruct.

Expected: A candidate validation method and the values it compares.

If stuck: For failed methods or resource clues, decode a fresh directory with apktool d app.apk -o decoded-app and inspect smali/resources.

Caveat: JADX cannot decompile every method correctly. Apktool is pinned to 2.7.0; do not copy newer-only flags.

pycdc (Decompyle++) (kali-110) · Fernflower (kali-38) · js-beautify (kali-75)

Image/date → metadata clueA locally supplied original image image.jpg.

ExifTool (windows-14)

  1. Run exiftool -a -u -g1 image.jpg to retain duplicate tags and their groups.
  2. Compare GPS, camera and date fields across groups; record any explicit time-zone offset and contradictory values.
  3. Corroborate the selected clue with the supplied context or an independent public source; record its URL and date.

Expected: A sourced location/date hypothesis with conflicts kept visible.

If stuck: If metadata is absent, use visible clues and the public-source route; absence does not establish provenance.

Caveat: ExifTool runs in WSL. Metadata may be forged, stripped or copied; a timestamp without an offset does not establish UTC.

Hash/password → bounded candidatesA known-format hash file hashes.txt and a short local candidate list candidates.txt; replace MODE.

hashcat (kali-59) · John the Ripper (jumbo) (kali-73) · hashid (kali-60) · rockyou.txt (Kali 'wordlists' package) (kali-120)

  1. Match the complete hash syntax and source format to hashcat example hashes; select the numeric MODE. hashid guesses alone are insufficient.
  2. Run hashcat -m MODE -a 0 hashes.txt candidates.txt --runtime=60 for a bounded dictionary attempt.
  3. Run hashcat -m MODE hashes.txt --show; validate any recovered value against the supplied artifact.

Expected: A recovered candidate or a bounded exhausted/paused attempt with no match.

If stuck: For an archive/document requiring conversion, use the matching installed John jumbo converter and format; a parser/backend error is not an exhausted search.

Caveat: Check supported modes and compute backend locally. No match only rejects tried candidates. Keep password output private; preserve the installed wordlist.

RSA → specific weakness → checked resultA textbook RSA public key key.pub and an evidenced weakness.

RsaCtfTool (windows-30) · Python 3 (windows-7) · SageMath (kali-125) · crypto-attacks (kali-22)

  1. Run RsaCtfTool --dumpkey --key key.pub to inspect n and e; compare them with the challenge clues.
  2. If a small private exponent is the hypothesis, run RsaCtfTool --publickey key.pub --attack wiener --private; otherwise choose an attack only after checking its prerequisites.
  3. For recovered factors, verify p * q == n; for a recovered plaintext integer m and ciphertext c, verify pow(m, e, n) == c in local Python.

Expected: A recovered factor/key/plaintext checked against the original RSA parameters.

If stuck: A failed attack does not disprove RSA. Use SageMath or crypto-attacks only when the supplied algebra matches a specific supported attack.

Caveat: RsaCtfTool runs in WSL; launcher/flags may differ locally. Avoid all-attacks defaults and external factor services. The equality check assumes textbook RSA integers.

Verification: Source-reviewed; not executed on competition machines.

ripgrep (rg) (kali-119) · jq (windows-21) · Python 3 (windows-7) · ZBar (windows-19)

Challenge endpoint → protocol → interactionAn assigned HOST and PORT; replace these placeholders and restrict requests to that endpoint.

Nmap (with Ncat / Nping) (kali-94) · Impacket (kali-68) · socat (kali-127)

  1. Run nmap -sV -p PORT HOST to check the specified port and likely service.
  2. For a plaintext TCP challenge, run ncat HOST PORT; for a specified TLS service use ncat --ssl HOST PORT.
  3. Read the banner/prompt, send one protocol-appropriate input and record its response before automating.

If stuck: No response: check VPN, host/port and TLS requirement. Use Impacket for an actual SMB task or socat only for a concrete transport need.

Caveat: A service guess is not proof. Ncat connects here; it does not start a listener. Do not send arbitrary text to an identified binary protocol.
