Specialist task workflows

Use these notes with the task routes when the core workflows do not cover the format or question. Keep the original artifact, work on a copy, and record the observation that justifies each next step. The procedures do not rely on AI Overview; external links are optional references. They cover the prepared routes, not every possible challenge.

Forensics · Malware · Web · Native and managed reversing · OSINT · Crypto

Supplied Wi-Fi capture: check evidence before candidates

Inspect the capture for the target network and PMKID or EAPOL exchange. Keep the BSSID/ESSID and message completeness with the source packet numbers. Choose a new, nonexistent output path before hcxpcapngtool -o NEW_capture.22000 capture.pcapng: hcxtools can append to existing files. Read converter warnings and confirm the new records match this capture, rather than trusting a nonempty file from an earlier run. Match the output format to mode 22000, then follow the Hashcat guide with a local wordlist. Exhausted covers only the candidates tested. If conversion yields no record, revisit capture and converter evidence before drawing any password conclusion.

Check: Relate a recovered candidate to the selected network and original capture. On a self-authored beacon plus complete M1/M2 capture, hcxtools 7.1.2 emitted one mode-22000 record and Hashcat 7.1.2 recovered the toy password. Reusing the output path appended a second record; incomplete captures exited zero with no new record, and invalid capture input failed. These controls support a fresh output path and record check, not competition-machine behavior. This workflow reads supplied files only; it does not require or justify active capture, deauthentication or uploading packets. Hashcat mode 22000.

Windows EVTX: keep a source-backed timeline

Choose the relevant log channel and event ID from the question. Run one copied EVTX file at a time so its path and hash stay attached to the result; Chainsaw's JSON search result does not include the source filename. For a PowerShell script-block clue, chainsaw search -t 'Event.System.EventID: =4104' COPY/Selected.evtx --json -q uses the locally tested 2.16.5 syntax. Require exit status zero and valid JSON before interpreting an empty array as no match: a malformed file can exit nonzero after printing incomplete JSON. Record the source file, Event ID, record ID, host/account, timestamp and time zone for a hit before relating it to another event. Use rule-based Chainsaw hunting only with a local rule set and matching mapping; Hayabusa is an alternative for timeline-led work, but its command names depend on the installed version.

In the bundled autosolve.py EVTX record, locator, record_number and header_timestamp identify the file record header; event_record_id and timestamp come from XML Event.System. The intelligence lead repeats the XML record ID for cross-tool matching. Check timestamp_basis: if XML TimeCreated is absent or invalid, timestamp falls back to the header time. Retain system_time_raw and the source record when comparing tools; the locally tested parsers differed by one microsecond on the sample event.

Check: Open the matching source record and explain the time ordering and the fields supporting the claim. On an upstream sample EVTX, Chainsaw 2.16.5 returned one Security 4625 record and [] for 4104; malformed input returned an error and incomplete JSON. The sample is a syntax check, not evidence about a challenge. An absent log, parser error or rule hit cannot establish absence or malicious intent. Chainsaw search and hunt · Hayabusa.

Registry hive: keep key, hive and transaction state together

Identify the hive type and preserve its transaction logs with a working copy. On Kali/WSL, the upstream RegRipper rip.pl is not directly executable: from its installed directory, use perl ./rip.pl -l to list plugins and perl ./rip.pl -r HIVE -p PLUGIN on the copied hive. This source build needs Parse::Win32Registry and the patched WinNT modules named in its README; check those prerequisites before interpreting a failed run. Use perl ./rip.pl -r HIVE -d to check the hive's dirty state. A clean and a dirty hive can both return exit zero; this option does not replay LOG1/LOG2. A plugin can also exit zero while reporting that its key is absent, so read the output and keep the plugin name and source hive with any hit. Use an approved second registry view or related artifact to corroborate a decisive value.

Check: Record the key/value, source hive, plugin, and exact timestamp basis. An isolated RegRipper 3.0 check listed 257 plugins; applets found a known key in a public NTUSER hive, while a SAM control exited zero with no matching key. Dirty and clean controls produced distinct -d messages. A key's last-write time does not identify the person who changed a particular value. RegRipper README · RegRipper CLI.

SQLite or SQLCipher artifact: preserve WAL rows and read a copy

Collect a consistent snapshot of the database with matching -wal and -shm sidecars when present; separately copying files while an app writes can produce an inconsistent set. In a writable analysis directory, sqlite3 -readonly COPY.db '.tables' and sqlite3 -readonly COPY.db '.schema TABLE' reveal the structure without opening the database for writes. Query only the rows relevant to the clue, order them explicitly, and establish each time field's epoch and time zone before converting it. Hindsight can enrich supported browser profiles, but direct SQLite rows remain the fallback when its parser does not match the version.

If the copied database is SQLCipher-encrypted and the clue supplies its passphrase, plain sqlite3 cannot read its schema. In a local terminal, send the key through stdin so it does not appear in shell history or process arguments. SQLCipher derives the key only when it first reads data: set the key and any evidenced producer-specific cipher settings before the first schema query. This example checks the default SQLCipher 4 settings with the installed sqlcipher CLI:

python3 - COPY.db <<'PYCODE'
from getpass import getpass
import subprocess, sys
key = getpass('SQLCipher passphrase: ')
sql = "PRAGMA key = '" + key.replace("'", "''") + "';\n"
# Add evidenced cipher compatibility settings here, before the first SELECT.
sql += "SELECT count(*) FROM sqlite_master;\n"
sql += "SELECT name FROM sqlite_master WHERE type='table' ORDER BY name LIMIT 20;\n"
subprocess.run(['sqlcipher', '-batch', '-bail', '-readonly', sys.argv[1]],
               input=sql, text=True, encoding='utf-8', check=True)
PYCODE

After a successful schema read, select only the evidenced row with an ordered, bounded query on the same private copy. A raw hex key needs SQLCipher's documented blob-literal form; the prompt above treats its input as a passphrase. A wrong key, incompatible cipher settings, malformed input or missing sidecar can all make the schema read fail; PRAGMA key by itself proves nothing. Do not put the key in -cmd, shell arguments, logs or shared notes. An isolated SQLCipher 4.18.0 test read one known row from a toy encrypted database; plain SQLite and a wrong key failed, and -readonly rejected an update.

Check: Tie a selected row to its table, database copy, sidecar state and source application. Read-only WAL access has conditions; a missing WAL or failed open is not proof that a recent row never existed. The CLI may create a working -shm file beside the copy. Browser profile: trace a selected visit

Use a coherent copy of one supplied Chrome/Chromium or Firefox profile. Keep History or places.sqlite with any matching -wal and -shm files; note whether the browser was running when copied. Record the browser/profile version and source path. Check help through the actual runnable launcher (VENV/bin/python VENV/bin/hindsight.py --help if the .py file is not executable), using the Python interpreter from that Hindsight installation and its required reader dependencies. Only if that same launcher lists --only, run it with -i PROFILE_DIR --only history (-b Firefox only if detection needs it), passing explicit absolute private paths for output (-o), log (-l) and temporary copies (--temp_dir). Inspect the parse/skip/error report. A disposable PyPI pyhindsight 20260600 install had a non-executable launcher, needed the separately listed ccl_chromium_reader dependency, and lacked --only even after that dependency was installed. Use the SQLite fallback below when the local build cannot filter history; a default full-profile export can also parse cookies and passwords.

An isolated upstream source revision bundled its Chromium reader and passed a filtered Chrome history check with this launcher form:

private_run=$(mktemp -d /tmp/hindsight.XXXXXXXX)
VENV/bin/hindsight -i PROFILE_DIR -b Chrome -f jsonl \
  -o "$private_run/history" -l "$private_run/hindsight.log" \
  --temp_dir "$private_run/temp" --only history

The benign profile held one known visit and two downloads. The filtered output contained the visit only and reported downloads skipped; an unfiltered control contained all three records. This source build displayed the same 2026.06 version family as the incompatible PyPI install, so use its pinned revision and the installed help rather than the version label to choose the command. Its defaults append a log under the installation and place transient database/WAL/SHM copies there; failed or interrupted runs may leave copies. Keep the private run directory for review, check for remaining copies, and remove it when no longer needed. Filtering the output does not guarantee that plugins or version detection never read other profile metadata. Verify the exact artifact types; a download can have a type containing the word history, so do not filter JSONL by that substring.

Check the copied schema first: sqlite3 -readonly COPY/History '.schema urls' '.schema visits' or sqlite3 -readonly COPY/places.sqlite '.schema moz_places' '.schema moz_historyvisits'. Then select a small, evidenced URL set, replacing MARKER locally:

sqlite3 -readonly COPY/History "SELECT v.id,u.url,v.visit_time,datetime((v.visit_time-11644473600000000)/1000000,'unixepoch') FROM visits v JOIN urls u ON u.id=v.url WHERE u.url LIKE '%MARKER%' ORDER BY v.visit_time,v.id LIMIT 20;"
sqlite3 -readonly COPY/places.sqlite "SELECT h.id,p.url,h.visit_date,datetime(h.visit_date/1000000,'unixepoch') FROM moz_historyvisits h JOIN moz_places p ON p.id=h.place_id WHERE p.url LIKE '%MARKER%' ORDER BY h.visit_date,h.id LIMIT 20;"

Use only the query matching the source browser and confirmed schema. Keep raw times alongside UTC conversions; check the time basis before relying on a displayed date. SQLite may create a working -shm beside the copy. Compare a decisive row with a separate known log or download record and preserve the exact profile/database path. A stored visit may come from sync, import or another browser action; it does not identify a human viewer. A missing row can also mean a different profile, absent WAL, filtered output, unsupported schema or parser error. Android app data: inspect one preference key

Require a supplied, accessible app-data extraction; an APK does not contain a user's private app state. Preserve the original and record the Android user, package, source path and file hash before copying one evidenced SharedPreferences XML file and any matching .bak. Android may restore that backup on load, so compare both copies if present; an extraction made during a write may not identify one active value. App versions and users can have different files. If a complete extraction and the approved ALEAPP build are available, check its local help. On Kali/WSL, use the installed launcher with a fresh private run directory:

umask 077
private_run=$(mktemp -d /tmp/aleapp.XXXXXXXX)
mkdir "$private_run/report" "$private_run/tmp" "$private_run/config"
TMPDIR="$private_run/tmp" XDG_CONFIG_HOME="$private_run/config" \
  python3 aleapp.py -t fs -i EXTRACTION_DIR -o "$private_run/report"

Use aleapp instead of python3 aleapp.py if that is the installed launcher. ALEAPP can put exact copies of matched source files, source paths and logs under the report; keep the entire run directory private. The private TMPDIR covers standard-library temporary copies seen in its source, not every possible plugin file. A benign synthetic extraction produced two known preference rows from one source file and an exact report copy; an unrecognized app path produced no match. Keep parser/module errors and source-file references; a report row is a lead, not proof that another file or user had the same state.

For a copied regular UTF-8 XML file of at most 1 MiB, select one named string, boolean or decimal int/long key locally with approved Python. Do not dump every preference:

python3 - COPY.xml KEY <<'PYCODE'
import os, re, stat, sys
from xml.etree import ElementTree as ET
if len(sys.argv) != 3:
    raise SystemExit('supply a copied XML file and one key')
fd = os.open(sys.argv[1], os.O_RDONLY | os.O_NOFOLLOW | os.O_NONBLOCK)
with os.fdopen(fd, 'rb') as source:
    if not stat.S_ISREG(os.fstat(source.fileno()).st_mode):
        raise SystemExit('not a regular file')
    data = source.read(1024 * 1024 + 1)
if len(data) > 1024 * 1024 or b'\x00' in data:
    raise SystemExit('large or non-UTF-8 XML is unsupported')
try:
    data.decode('utf-8')
except UnicodeDecodeError:
    raise SystemExit('non-UTF-8 XML is unsupported') from None
if b'<!DOCTYPE' in data.upper():
    raise SystemExit('DTD-bearing XML is unsupported')
try:
    root = ET.fromstring(data)
except ET.ParseError:
    raise SystemExit('malformed XML') from None
rows = [item for item in root if item.get('name') == sys.argv[2]]
if root.tag != 'map' or len(rows) != 1 or len(rows[0]):
    raise SystemExit('missing, duplicate, or structured key')
item = rows[0]
if item.tag not in ('string', 'boolean', 'int', 'long'):
    raise SystemExit('unsupported preference value type')
if item.tag == 'string':
    value = item.text or ''
else:
    value = item.get('value')
    if value is None or len(value) > 64 or (item.text or '').strip():
        raise SystemExit('malformed primitive value')
    if item.tag == 'boolean' and value not in ('true', 'false'):
        raise SystemExit('invalid boolean value')
    if item.tag in ('int', 'long'):
        if not re.fullmatch(r'-?[0-9]+', value):
            raise SystemExit('invalid integer value')
        number = int(value)
        bits = 32 if item.tag == 'int' else 64
        if not -(1 << (bits - 1)) <= number < (1 << (bits - 1)):
            raise SystemExit('integer exceeds Android type range')
print(item.tag, repr(str(value)[:160]))
PYCODE

Check: Tie the selected key, stored type and value to the copied XML and an independent app/configuration clue, database row, log or known case observation. For an app database, follow the SQLite/WAL workflow with its matching sidecars. A numeric preference has no universal time epoch. Missing keys, conflicting XML/.bak, non-UTF-8 or unsupported value types, malformed XML, a different Android user, unavailable/unsupported ALEAPP modules or an incomplete extraction leave absence inconclusive. Keep private values out of shared notes. Android SharedPreferences · AOSP XML implementation · ALEAPP CLI · Python XML security.

Android Preferences DataStore: select one key from a copy

An accessible app-data extraction may contain files/datastore/*.preferences_pb instead of SharedPreferences XML. An APK alone does not contain the user's stored preferences. Record the Android user, app package, original path and hash; work on a stable copy. Check that the file is Preferences DataStore. App-defined Proto DataStore files need their own schema and are outside this reader's scope.

For one exact key, run the bundled standard-library reader from the offline kit in a private session:

python3 scripts/templates/datastore_pref.py COPY.preferences_pb KEY

It accepts one regular file up to 1 MiB and reports the selected key's stored boolean, int32, int64 or string value. It validates every map entry, rejects duplicates and truncated or ambiguous wire data, and does not print other keys. Valid float, double, string-set and byte-array values on other keys do not block selection; a requested key of those types needs another parser. A missing key means only that it was absent from this copy. Keep selected values out of shared notes.

Check: Match the reported key, type and source path to independent app code, configuration, log or case evidence. A numeric value has no universal timestamp unit. If ALEAPP is installed, use its source-file reference and parser version as a lead, then confirm the decisive value against the copied file. Another Android user, app version, file, incomplete extraction or an unsupported selected type remains possible. Android DataStore · AndroidX Preferences schema.

iOS plist: inspect one named field

Work on a copy of a supplied XML or binary plist. Record its original path, application/container context and hash. The approved Python standard library reads both formats without an added dependency. Inspect a named key path, rather than dumping a whole potentially private file. Pass each nested dictionary key or list index as a separate argument:

python3 - COPY.plist APP KEY <<'PYCODE'
import datetime, plistlib, sys
with open(sys.argv[1], 'rb') as source:
    data = plistlib.load(source)
if len(sys.argv) < 3:
    raise SystemExit('supply at least one key')
value = data
for part in sys.argv[2:]:
    value = value[int(part)] if isinstance(value, list) else value[part]
scalar = isinstance(value, (str, int, float, bool, datetime.datetime))
print('/'.join(sys.argv[2:]), type(value).__name__, str(value)[:160] if scalar else '[structured or binary value]')
PYCODE

A missing key or out-of-range index raises an error; inspect the actual structure and field definition before choosing another path. If a complete extracted filesystem and approved iLEAPP are available, check its local help and create a fresh mode-700 parent with precreated report, tmp and config directories as in the Android example (use /tmp/ileapp.XXXXXXXX). Set TMPDIR and XDG_CONFIG_HOME to those private subdirectories before ileapp -t fs -i EXTRACTION_DIR -o PRIVATE_REPORT or the installed python3 ileapp.py equivalent. iLEAPP stages matched source copies, paths and logs; keep the whole report private. An isolated iLEAPP 2026.4.6-dev run on a self-authored SystemVersion.plist returned three known fields and a byte-identical source copy; the same bytes at an unrecognized path produced no match. Tie a selected report field back to its original plist and independent app or case context. Numeric times need their field-specific epoch and units before conversion. Encrypted/incomplete backups, unsupported keyed archives, malformed plists and parser errors leave absence inconclusive. Competition-machine behavior remains unverified. Do not paste private report values into shared notes. Python plistlib · iLEAPP CLI.

Git history: recover the exact source revision

Work on a copy of the supplied repository. git -C REPO status --short separates working-tree files from committed history; git -C REPO log --all --oneline --decorate shows the refs actually present without fetching anything. For a known path, git -C REPO log --all --follow --oneline -- PATH can trace simple renames. Choose a commit that contains the file and inspect its exact blob with git -C REPO show COMMIT:PATH. If the clue points to a deletion commit, select the parent in which the path still existed; do not assume the current branch has the only relevant history.

Check: Keep the commit ID, path, blob bytes and source ref together. A Gitleaks match can guide a focused inspection but is not proof that a historical credential is valid. Avoid broad terminal dumps and do not copy recovered secrets into shared notes. Missing objects in a shallow or incomplete repository leave the question open. Git log · Git show · Gitleaks.

Unknown executable: separate format from behavior

Start with file_intel.py or file, then use Detect It Easy to confirm format and architecture. For a supported native executable, capa -v sample.bin gives capability leads and the locations behind them. Open one relevant location in the matching disassembler; check the surrounding code or bytes before describing behavior. A decoded string, import or capability label alone does not prove that a path executes. Keep unknown programs in the intended isolated analysis environment rather than running them as a first look. Practice the evidence distinction.

If the executable is identified as Go, especially when its normal symbols are stripped, choose a new path in a private analysis directory and run GoReSym -t -p sample.bin > PRIVATE_DIR/NEW_go.json on a copy. Check Version, Arch, OS, UserFunctions names and start/end addresses, Files, and retained Types; align a selected function address with the disassembler. Keep the JSON private because embedded source paths may be sensitive. A locally built stripped Go 1.26.5 ELF yielded a known function, source path and retained struct; a stripped C ELF returned no valid Go pclntab. Optimization can remove types, and a parser failure does not prove a file is not Go. GoReSym usage.

Check: Record the file type, one indicator with its offset/address, the code or bytes that support it, and one claim the evidence does not establish. If the packer or architecture is uncertain, resolve that before trusting a decompiler view. capa usage.

Linux executable: check one observed file creation

Use this file-creation route only after static triage suggests a specific new output file worth checking. Run an unknown executable only in an independently isolated, authorized analysis environment; a temporary directory and resource limits do not contain it. Disable access to host files and services as the analysis setup requires, and keep inputs and traces private. Start the selected run and a no-action control from identical clean states.

Inside that environment, choose a new private trace path and run strace -f -e trace=%file -o NEW_PRIVATE_TRACE ./PROGRAM INPUT. Replace PROGRAM and INPUT with the inspected executable and selected input. -f follows child processes; %file selects filename-taking syscalls, including openat, but does not record write contents. For one expected output path, inspect the call's arguments and return value, then read the actual file bytes or confirm its absence. Reset to the same clean state, run the no-action input, and compare its trace and file state. Ignore routine loader/library opens unless they answer the question.

Check: Keep program and input hashes, the isolation setup, exact command, relevant trace lines, output bytes, and the matched control outcome. A successful openat alone does not prove a write; the independent file check establishes the observed effect. A quiet trace or failed call under one input does not rule out other behavior. Check strace --version and strace --help on competition Kali; the prepared local image has 6.8 while the workbook lists 7.0. strace manual · strace project.

Office or PDF: locate code without executing it

For Office, use olevba document.docm to list VBA streams and inspect the extracted code. Treat reported suspicious keywords as triage hints; trace the actual macro entry point and any decoded strings. For PDF, inspect the rendered pages, then use qpdf --check, qpdf --list-attachments and qpdf --show-pages in the PDF workflow. Use pdfid.py to count noteworthy object types and pdf-parser.py to inspect the identified object. Do not open a recovered attachment or macro as a program merely because extraction succeeded.

Check: Tie any claimed code to a stream or PDF object number and explain whether it is embedded, referenced, or actually invoked. A count or keyword by itself is not an execution trace. olevba reference · qpdf command reference.

Bundles: identify before choosing an extractor

Confirm PyInstaller, ASAR or UPX from the file structure and the bundle route. Extract into a new directory with the matching approved tool. Keep the original and note the reported runtime or entry point. For PyInstaller, check the reported Python version before using a bytecode decompiler; for ASAR, inspect package.json and the named entry file. UPX decompression changes the file under examination, so compare hashes and paths before switching analysis to the unpacked copy.

Check: Identify the output file that contains the next code path and why. Extraction does not establish that decompiled source is complete or that the extracted program is safe to run. PyInstaller extractor · ASAR usage · UPX documentation.

YARA: correlate observed bytes across a copied corpus

Use this corpus route after inspecting two specific byte indicators in a seed artifact. A rule detects their coexistence; it does not identify malware or show that code ran. Keep the original corpus untouched. For a flat, small practice corpus, reuse the bundled two-indicator rule from Practice Block 6:

mkdir -p work
corpus=$(mktemp -d ./work/yara-corpus.XXXXXX)
cp research/learning/practice/match.txt "$corpus/positive.txt"
cp research/learning/practice/near-miss.txt "$corpus/near-miss.txt"
printf 'training-marker only\n' > "$corpus/marker-only.txt"
printf 'harbor alone\n' > "$corpus/word-only.txt"
printf 'training-marker harbors\n' > "$corpus/harbors.txt"
yara -s research/learning/practice/training.yar "$corpus"

Expect only positive.txt to match. -s prints each matched string's identifier, hexadecimal byte offset and bytes; inspect those bytes at the reported offsets in the copied file. The marker-only and word-only files test that both indicators are required; the near miss tests spelling, while harbors tests the fullword boundary. A real rule should use indicators evidenced in that case, with a positive and close negative from the same input family. Scan selected files or one bounded directory first. For nested directories, confirm the supplied root itself is a real directory, then use yara -s -r -N rule.yar copied-corpus; -r recurses and -N skips symlinks found inside it. An explicitly supplied symlink target can still be followed. Do not scan an unbounded tree by habit.

Check: Record the rule, file hashes, exact matched bytes and offsets, and outcomes for all five files. If the positive fails, check encoding and your rule syntax. If a negative hits, narrow the rule and rerun all controls. A hit only prioritizes another file for independent format, code and context inspection. YARA CLI · YARA rule syntax.

Endpoint discovery: distinguish a hit from a wildcard

Request one invented path on the assigned host and save its status, size, body and redirect target. Run the bounded endpoint route with a short local list. Compare candidate paths with the invented path, then verify a promising candidate in a browser or Repeater. http_probe.py can record one unauthenticated response without following redirects; use Repeater for cookies, CSRF or a multi-request flow.

Check: Show a response difference beyond the path string itself. Equal status codes can still have different bodies; different status codes can be authentication redirects rather than an exposed endpoint. ffuf reference.

Targeted web test: keep the hypothesis and control together

Begin with a working request to the assigned service. Send it unchanged twice in Burp Repeater, noting changing cookies, CSRF values and response content. Name the suspected input and vulnerability class from observed behavior. Change only that input, then send a nearby negative control and restore the baseline. The local PayloadsAllTheThings copy can supply syntax once its prerequisites match the observed parser or rendering context; it is a lookup, not evidence that a payload worked.

Check: Record the original, changed and negative-control responses and any downstream state. A status change, error message or reflected payload alone may leave multiple explanations; choose the next observation that separates them. Keep credentials and challenge content local. Repeater guide.

Reflected input: separate output from execution

Start with a working request to the assigned application. Replay it unchanged twice in Burp Repeater so redirects, session state and changing response fields are visible. Change one input to a unique inert marker and save the request, Content-Type and relevant raw response bytes. Locate the marker in its exact HTML text, quoted attribute, URL, script or other context. http_probe.py can record a single stateless request; use Repeater when cookies, CSRF or multi-request state matter.

On the selected Repeater response, use Show response in browser and open the unique URL in Burp’s browser or Chrome configured through Burp. Burp serves the selected main response without forwarding a new request to the application; page assets may still generate requests. Compare its raw source with the parsed DOM and console; note enforced Content-Security-Policy separately from Report-Only. If a script-execution check is justified for the observed context, use a harmless local DOM marker and no cookie access or external request. For a plain HTML text insertion only, one candidate is <script>document.documentElement.dataset.ctfProbe='case-marker'</script>; other contexts need different syntax. Check that the marker appears in the DOM only for the changed request, then repeat the unchanged request and a nearby negative control. A reflected string or injected element without the expected effect is not proof of script execution. A CSP block is evidence about that test and policy, not a universal safety result.

Check: Keep the source request, raw response, parsed context, browser/CSP observation and negative control together. If the value is missing or the response changed, recheck redirects, cache, encoding, session and client-side rendering before drawing a conclusion. Do not spray payload lists or access secrets. Suspected SQL input: compare paired conditions

Start with a working request and replay it unchanged twice in Burp Repeater. Change one suspected parameter with a syntax probe, then compare a condition expected to be true with a closely matched false condition appropriate to the actual input type and quote context. Keep a non-SQL negative control and refresh expiring sessions or CSRF values. A single quote error or changed HTTP status can also come from validation or a generic exception; seek a repeatable body or state difference that follows the condition. Only then consult the matching offline PayloadsAllTheThings topic or target one saved request and parameter with approved sqlmap.

Check: State the original, true, false and negative-control observations and why SQL evaluation explains them better than cache, session or input validation. Do not treat an automated report as independent proof without an application-level check. PortSwigger SQLi detection.

URL input: distinguish server fetch from browser navigation

For a URL-like field, observe the unchanged request first: a browser redirect and a server-side fetch have different evidence. Substitute one benign destination within the assigned scope that returns a unique marker, plus a malformed or blocked destination as a control. Use Repeater to compare responses and a challenge-provided request log if one exists. A reflected URL, redirect, or status change alone does not prove that the application server made the request; asynchronous jobs and caching also change what you can see.

Check: Identify the marker or logged request, its destination and the server-side step that produced it. If no such observation exists, keep SSRF as a hypothesis and do not probe arbitrary internal addresses or external callback services. PortSwigger SSRF.

Object reference: compare two known owners

Use two permitted principals with objects whose ownership is already known. Capture A's normal object request and B's own-object request in separate sessions. Under B's authenticated session, change only the reference to A's object; compare the full content or state with B's own object and a nonexistent-object control. A generic 200 page or public/shared record is not a cross-owner read. Keep tokens private and avoid random ID enumeration as a substitute for ownership evidence.

Check: Name the intended access rule, both object owners, the session used for each request, and the data or action the server actually allowed. Without a second principal or reliable ownership evidence, report the authorization question as untested. PortSwigger IDOR.

File path input: verify an outside-root read

Use a file-serving request on the assigned service and establish its intended serving root. Choose one allowed file, one missing filename, and one permitted benign file known to be outside that root with bytes known independently from the HTTP response. If the outside file's location or bytes are unknown, record a path-traversal lead rather than a confirmed read. Save the unchanged request and its raw response. In Burp Repeater, repeat the allowed-file request, send the missing-file control, then change only the file input to one relative traversal path reaching the known outside file. Preserve the other fields and session; inspect and retain the exact query bytes sent, including the chosen path encoding. Keep the request count small and within the assigned scope. The optional WEB05 selected-input check compares a candidate marker against two missing-file controls; it preserves untouched raw query fields but re-encodes the selected value and does not establish file provenance.

Check: Compare raw response body bytes with the independently known outside file, and confirm that this file lies beyond the intended root and was not deliberately served through that endpoint. Repeat the selected request only if session or cache behavior needs calibration. A reflected path, familiar filename, generic 200, error text, redirect, or WEB05 lead alone is inconclusive; a body wrapper or transformation needs an independently justified byte comparison. Do not request unrelated private files or widen into recursive path spraying. OWASP directory traversal testing · PortSwigger path traversal · Burp Repeater.

Cross-site request: establish a state change

Use only a permitted test account and a reversible action with a fresh state readout. In Chrome, perform one legitimate same-site action and capture its method, Content-Type, body, session cookie attributes, CSRF token, Origin, and Sec-Fetch-Site in Burp. Record the state before and after with a unique marker. A response status or echoed value is transport evidence, not the state result.

Copy the one-click form template, match its GET/POST method and form encoding, replace its placeholder action and fields, and serve it from a different site on loopback with approved Python. A different port alone changes the origin but may leave the site the same. In the same disposable browser session, click once and inspect the browser request. Record whether the session cookie was attached and whether the server received the intended fields. Compare against an unauthenticated or invalid-token control; use a new marker or restore the state between attempts. A plain form cannot reproduce other HTTP methods, JSON/custom headers, or obtain a fresh target-only CSRF token.

Check: Read the application state independently after each attempt and tie any change to the cross-site request, its cookie/session and a control that did not change state. A blocked CORS read, 200, redirect or SameSite label alone is inconclusive. If the browser omitted the cookie or the action had no observable state, report that limit rather than inferring a universal CSRF defense. OWASP CSRF testing · MDN CSRF · MDN SameSite.

JWT: decoded claims are not trusted claims

Save one token from a working request in a private local file. Run the read-only jwt_inspect.py to display its header and payload without sending it anywhere. This parses a three-part JSON Web Signature token; it does not verify its signature, expiry, audience or server acceptance. Keep the original request, then use the approved JWT and Repeater tools to compare server responses to one relevant changed token and a negative control. An edited role claim visible in a decoder is only edited text until the server accepts it in the intended action.

Check: State what the server did with the original and changed token, and whether authentication, authorization or a separate application condition explains the result. Do not paste live tokens into online decoders or commit the private file. JWT attacks and token structure.

Native crash: establish control before a payload

Confirm the executable format and architecture, then run the installed checksec --file=./challenge form for an ELF. Reproduce the supplied input path under GDB and compare one crashing input with a nearby noncrashing control. A cyclic pattern helps measure an offset only after the crash shows your bytes in a relevant control value; cyclic_find must use the same subsequence size and byte order as the generated pattern. Record the measured offset and the actual overwrite or leak. PowerShell source: recover only evidenced literals

Copy and hash the supplied .ps1, .psm1, .psd1 or text command first. On Linux/Kali/WSL, the bundled REV11 helper reads source bytes without invoking PowerShell; it is not a native Windows helper. Check python3 scripts/autosolve.py doctor --profiles reversing --self-test; inspect malware_reversing.powershell_constants because other reversing operations can keep the overall status partial. Extensionless command text routes when a powershell, powershell.exe, pwsh, or pwsh.exe command starts a line within the first 4 KiB, optionally path-qualified or quoted. Use a fresh private run root: decoded strings and source paths can be sensitive.

The helper recognizes bounded literal concatenation, literal [Convert]::FromBase64String(...) and UTF-16LE -EncodedCommand values, including two levels of nested encoded commands. It records the original source byte span, line and column, any derived span, and each transform. Match those locators to the original bytes; compare a promising result with a separate clue or valid local check. A supported literal elsewhere in the file does not clear a dynamic-expression warning; here-string contents are data and are skipped. A static candidate is neither proof that code ran nor an accepted answer. The worker has a five-second time budget, 256 MiB address-space limit, 256 KiB source limit, and 64-record/64 KiB output bounds. No security sandbox is claimed.

Check: A self-authored UTF-16LE encoded command yielded the exact known nested literal bytes and retained its Base64 source span; a comment containing similar syntax and a dynamic variable produced no decoded proof. A modified source invalidated the prior candidate on resume. First identify one supplied Linux x86/x86-64 ELF and the path by which it reads the proposed answer. {"checker":{"channel":"argv","length":5,"find":{"stdout":"accepted"},"avoid":{"stdout":"rejected"}}}

Public image: corroborate the visible landmark

Start with the original public image page and record its URL, creator, stated capture date and upload date separately. Note the camera viewpoint and two distinctive visible features before searching. For a public or otherwise explicitly permitted image, Chrome's Google Lens can search a selected region of its public page. For private challenge material, keep the image local and search only a description of its visible features. Open a candidate venue's own architecture and location pages, compare the visible structure and surroundings, then check one plausible same-city alternative. A search rank, caption, geotag or EXIF field supplies a lead; none independently identifies the photographed object. A camera coordinate is a viewpoint, not necessarily the object's address.

Public example: A CC0 Commons photo of Esplanade shows a curved dome with patterned sunshades beside the waterfront and a bridge. Esplanade's own architecture page describes its twin domes and triangular aluminium sunshades on Marina Bay; its visit page gives the venue's address. Only one dome is prominent in this photo. A CC0 Marina Bay Sands photo is also in the Marina Bay area, but shows three towers joined by a roof deck, matching the Marina Bay Sands hotel factsheet, not Esplanade's dome. Thus “Singapore/Marina Bay” alone fails the identification check. The Esplanade file page states 20 May 2012 for capture and 11 April 2021 for its Commons upload; those are different claims, and the camera date is not independently verified by the venue page.

XOR or reused stream: align bytes before inferring text

Convert each input to raw bytes and keep the original offsets. If two ciphertext positions used the same keystream byte, C1 XOR C2 = P1 XOR P2; this relation alone does not identify either plaintext. An independently known plaintext segment yields keystream bytes only at its aligned positions. Apply those bytes to the other ciphertext at matching positions. XORing a proposal back to the ciphertext checks arithmetic only; independent evidence must support the proposed text and shared-stream assumption. The local known-key XOR helper is useful once a key and its repetition pattern are established; it does not recover unknown keys.

Check: Record the byte representation, alignment, known-plaintext source, recovered positions, arithmetic check and separate format or checker evidence. Leave unobserved positions unknown. A short segment should not be repeated across the file unless repeating-key XOR is evidenced. CTR can reuse keystream only where its counter blocks actually match. NIST CTR uniqueness · Cryptopals fixed-nonce exercise.

Declared AES: distinguish authentication from plausible output

Determine the exact bytes represented by the key and ciphertext and collect the mode's other inputs. GCM needs nonce, tag and any AAD; CBC needs its IV and padding rule; CTR needs the full initial counter block and layout. Use the matching approved tool or the bounded declared-parameter helper with secrets in a private hints file. openssl enc does not support GCM. A GCM result is validated only after its tag verifies. CBC and CTR outputs remain candidates until an independent MAC, known plaintext, strong format check or the challenge's checker supports them. Re-encrypting with the same parameters checks implementation consistency only; readable text and valid CBC padding do not authenticate plaintext.

Check: Preserve the mode, key size, representation, IV/nonce, tag/AAD or padding assumption and the independent result. Missing inputs mean the transform is unverified; do not silently try unrelated modes. NIST confidentiality modes · NIST GCM · OpenSSL enc limitations.

CBC padding oracle: establish the signal before recovery

Use this only for an assigned endpoint that accepts an editable CBC ciphertext. Record the exact byte encoding, block size, IV location, HTTP method, session and unchanged baseline response. CBC decryption changes a plaintext block when its preceding ciphertext block (or IV for the first block) changes. A padding oracle exists only if otherwise comparable requests reveal whether the final plaintext padding is valid. An error from a malformed length, MAC, AEAD tag, session rejection or application parser does not establish that signal.

On a copy of one sample, repeat the unchanged request, one prior-block mutation expected to disturb the final padding, and a control mutation outside the padding bytes where that position is known. Keep every other request field fixed; compare response status and body class rather than timing alone. Repeat each class to rule out transient behavior. A mutation can accidentally produce valid padding, so use more than one; stop if the responses are generic, unstable or rate-limited. For a one-block ciphertext with a prepended IV and a known one-byte PKCS#7 pad, flipping the IV's last byte by 0x01 forces a zero final byte, while flipping its first byte leaves that padding byte untouched. This is a calibration example, not an assumption about an unknown challenge.

The approved tool sends a two-block payload for each guess: an editable first block followed by the target block. Before using it, repeat the valid/invalid comparison with that shortened, two-block shape in the exact request field it would replace. Also try an arbitrary first block and check that it reaches the same padding-error class as the known invalid mutation; the tool starts its guessed block from zero bytes. A full-length sample can leak padding errors while the shortened probes fail an application length or format check. The command below applies when the endpoint accepts a prepended IV and ciphertext together in one field. If IV and ciphertext occupy separate fields, or the service requires an unchanged prefix or fixed length, verify the installed tool can express that layout; otherwise stop at manual calibration.

Only after this preflight, check padding-oracle-attacker --help on the approved Kali machine. The upstream CLI's positional arguments are URL, encoded ciphertext, block size and the observed error status or body substring. Replace every placeholder below with your own observed values; {POPAYLOAD} marks the single injection point. Use one concurrent request and disable its response cache:

padding-oracle-attacker decrypt 'https://ASSIGNED/decrypt?ciphertext={POPAYLOAD}' 'hex:IV_AND_CIPHERTEXT_HEX' 16 'OBSERVED_PADDING_ERROR' -c 1 --disable-cache

If the endpoint needs POST, a cookie or another encoding, use the installed CLI's -X, -H, -d and -e options after checking its help; do not guess their values. The upstream default is 128 concurrent requests and a local cache file. A benign one-block local exercise took 2,350 requests, so estimate the request count for the selected blocks and respect the assigned service's limits before running recovery. Keep ciphertext, session values and output in private local files. Recovered bytes are candidates until independent known plaintext, a strong source format, a valid MAC or the challenge checker supports them. On a generic-response control, this CLI even exited successfully with false plaintext; its exit status is not proof. Re-encryption and valid padding alone only check consistency.

Check: Record repeated response classes for both the original and two-block shape, the exact error marker and injected byte location, the candidate bytes and the separate evidence supporting them. The approved tool's installed version and availability are not guaranteed. Tool CLI · NIST CBC mode · PKCS#7 padding rule.

Secret-prefix hash: extend only the bytes the verifier signs

Use this when source or equivalent evidence shows the service checks a full SHA-1, SHA-256 or SHA-512 digest of secret || message, you have the exact original message bytes and tag, and the verifier will accept message bytes after the original. HMAC, hash(message || secret), truncated tags and unknown canonicalization do not meet these conditions. Confirm whether the service signs raw bytes, decoded query data or a parsed structure; padding includes 0x80 and zero bytes that a text-only path may discard. An arbitrary digest with a matching length is not evidence of a secret-prefix MAC.

The approved Kali tool is a Python module, not a documented CLI. Check python3 -c 'import hlextend; print(hlextend.__file__)' on that machine, then adapt this offline example. Replace every uppercase placeholder; known and append are hex-encoded raw message bytes, not printed URL text. The sample key length is illustrative: use only lengths justified by source or format, at most 32 candidates. This snippet prints candidates but sends no requests.

from urllib.parse import quote_from_bytes
import hlextend

known = bytes.fromhex("KNOWN_MESSAGE_HEX")
append = bytes.fromhex("APPENDED_BYTES_HEX")
old_tag = "FULL_ORIGINAL_TAG_HEX"
key_lengths = (12,)  # example only; replace with evidenced lengths
assert 1 <= len(key_lengths) <= 32 and all(n > 0 for n in key_lengths)

for key_length in key_lengths:
    sha = hlextend.new("sha256")  # use only the observed sha1, sha256 or sha512
    forged = sha.extend(append, known, key_length, old_tag)
    print(key_length, quote_from_bytes(forged, safe=""), sha.hexdigest())

The quoted value is one URL component containing the complete forged message, including padding; insert it into the correct field without a second encoding pass. If the endpoint uses a different transport, preserve those same bytes rather than assuming the URL form works. Keep the original tag and each resulting tag separate from the message. Try a single independently checked candidate first; stop on a parser error or byte transformation. A wrong-length candidate and an HMAC construction are useful negative controls. A locally computed digest or successful round trip proves arithmetic only; acceptance requires an independent verifier or a bounded authorized service check with an observable state change.

Check: Record the construction evidence, exact original bytes and tag, algorithm, justified key-length candidates, transmitted bytes, negative controls and independent acceptance result. Upstream hlextend supports SHA-1/256/512, but its competition-machine version and availability are unverified. hlextend API · HMAC construction.

ZipCrypto: prove the known bytes match the stored stream

Run 7z l -slt archive.zip and inspect the selected member's Encrypted and Method fields. The simple bkcrack case is ZipCrypto with a stored member and at least 11 supplied plaintext bytes, including eight contiguous; bkcrack adds one inferred ZIP header check byte for 12 total. Write the exact supplied bytes to a local file without an accidental newline. For a deflated member, the bytes to match are compressed data, so a familiar uncompressed file header may not apply. Use the bkcrack 1.8.1 tutorial command form only after the preconditions hold. Run the final two lines only if all entries share the same keys:

bkcrack -C archive.zip -c MEMBER -p known.bin
bkcrack -C archive.zip -c MEMBER -k KEY1 KEY2 KEY3 -d NEW_member
bkcrack -C archive.zip -k KEY1 KEY2 KEY3 -D NEW_archive.zip
7z t NEW_archive.zip

Validate the decrypted member bytes independently; a deflated result still needs decompression. Internal keys are not necessarily the original password. On a benign stored ZipCrypto fixture, isolated bkcrack 1.8.1 recovered the keys and exact known member bytes; a one-byte-wrong plaintext control found no keys.

Check: Record the member, encryption and compression methods, exact known-byte source, recovered-key output, and independent member validation. ZIP AES or a wrong plaintext offset belongs on a different route; a candidate-password search can use the Hashcat guide when its format and candidate evidence fit.
